# ตำแหน่งและเมนู (Positions & Menu Visibility) — Design

## Intent / ทำไมต้องทำ

วันนี้สิทธิ์ในแอปผูกกับ 3 ค่าคงที่ในโค้ด (`admin` / `supervisor` / `staff`) ซึ่งเป็นศัพท์เทคนิคที่ไม่ตรงกับตำแหน่งงานจริงของบริษัท และผู้ดูแลระบบมองไม่เห็นภาพรวมว่า "ตำแหน่งนี้ทำอะไรได้บ้าง เห็นเมนูไหนบ้าง" จากที่เดียว ต้องไปไล่ดูปุ่ม/โค้ดทีละหน้า

เป้าหมาย: ให้ admin ตั้งชื่อ "ตำแหน่ง" ให้ตรงกับงานจริง มองเห็นชัดเจนในตารางเดียวว่าแต่ละตำแหน่งทำอะไรได้ (อิงสิทธิ์พื้นฐานเดิม) และเห็นเมนูไหนบ้าง พร้อมเปิด/ปิดเมนูให้แต่ละตำแหน่งได้เอง — และวางโครงไว้ให้ง่ายต่อการเพิ่มเมนูใหม่ในอนาคตเวลาแอปมีฟีเจอร์เพิ่ม โดยไม่ต้องเขียนโค้ด permission ใหม่ทุกครั้ง

ผู้ใช้งานฟีเจอร์นี้ = admin เท่านั้น (คนเดียวกับที่เข้าหน้า "ผู้ใช้งาน" ได้ในปัจจุบัน)

อ้างอิงภาพหน้าตา/โครงสร้างที่ผู้ใช้ส่งมา (จากแอปอื่นของเขา — ใช้เป็นต้นแบบรูปแบบ UI เท่านั้น ไม่ใช่เนื้อหา เพราะโดเมนต่างกัน: แอปต้นแบบมีคำว่า "ไซต์", "SLA" ซึ่งไม่มีในระบบนี้):
- หน้า list: ตาราง ตำแหน่ง / สิทธิ์พื้นฐาน / ทำอะไรได้ / เมนูที่เห็น (x/y) / ผู้ใช้ (จำนวนคน) / จัดการ
- หน้า add/edit: ชื่อตำแหน่ง (บังคับ), สิทธิ์พื้นฐาน (บังคับ, เลือกจาก base tier), หน้าที่ (ไม่บังคับ, free text), เช็กลิสต์เมนูที่ตำแหน่งนี้เห็น

## Goals

1. เมนูใหม่ในแถบซ้าย **"ตำแหน่งและเมนู"** ต่อจาก **"ผู้ใช้งาน"** — โชว์/ซ่อนด้วย logic เดียวกับ "ผู้ใช้งาน" ทุกประการ (เฉพาะ admin เท่านั้นที่เห็น)
2. หน้าใหม่ `/settings/positions` (ชื่อ route จะยืนยันตอนลงมือทำ) — ตารางรายชื่อตำแหน่งทั้งหมด + ปุ่ม "เพิ่มตำแหน่ง" + ปุ่ม "แก้ไข" ต่อแถว ตามโครง UI ที่อ้างอิงด้านบน
3. ตำแหน่ง = (ชื่อที่ตั้งเอง, สิทธิ์พื้นฐาน 1 ใน 3 ค่าเดิมของระบบ — admin/supervisor/staff, หน้าที่ [free text ไม่บังคับ], รายการเมนูหลักที่มองเห็น)
4. "สิทธิ์พื้นฐาน" **ไม่ใช่ของใหม่** — คือ role เดิมที่มีอยู่แล้ว (`admin`/`supervisor`/`staff`) ตำแหน่งที่สร้างใหม่แค่เลือกว่าจะอิงสิทธิ์การกระทำ (ปุ่มแก้ไข/ลบ/อนุมัติ ฯลฯ) จากระดับไหนในสามระดับนี้ — การเช็ค `hasPermission(...)` และ role check ฝั่ง API ที่มีอยู่เดิมทั้งหมด **ไม่ต้องแก้แม้แต่บรรทัดเดียว**
5. เมนูที่ติ๊กเปิด/ปิดได้ = **เฉพาะเมนูหลักระดับบนสุดในแถบซ้าย** เท่านั้น ได้แก่: Bookings, Monitor, Vehicles, Drivers, Dashboard, Accidents, Complaints, **แบบฟอร์ม** (เมนูหลักแยกต่างหากจริงๆ ในโค้ดปัจจุบัน — ไม่ใช่เมนูย่อยของ Complaints — ชี้ไปที่ `/complaints/overview` รวม ภาพรวม/ประวัติ/4 ฟอร์มย่อยไว้ในตัวมันเอง), **ชั่วโมงทำงาน**, ผู้ใช้งาน, ตำแหน่งและเมนู — ไม่ลงรายละเอียดถึงเมนูย่อยภายในแต่ละอัน (เช่น 4 ฟอร์มย่อยใต้ "แบบฟอร์ม") ในเวอร์ชันนี้ (`/settings` ไม่รวมอยู่ในรายการนี้ เพราะปัจจุบันไม่มีลิงก์เมนูถาวรในแถบซ้ายอยู่แล้ว เข้าได้แค่ผ่านลิงก์รองในหน้าอื่น)
6. ปิดเมนูให้ตำแหน่งไหน = **ซ่อนจากแถบซ้าย + เปิดผ่าน URL ตรงไม่ได้ด้วย** (redirect ออก) — อิง logic เดียวกับที่ `/settings` และ `/settings/users` กันเส้นทางให้ staff ไม่ได้อยู่แล้วทุกวันนี้
7. สร้าง "ตำแหน่งมาตรฐาน" 3 ตำแหน่งตอน migrate ให้ตรงกับ role เดิมทั้ง 3 (ผู้ใช้เดิมทุกคนถูกจับคู่เข้าตำแหน่งมาตรฐานที่ตรงกับ role ปัจจุบันของตัวเองอัตโนมัติ — ไม่มีใครเสียสิทธิ์หรือเห็นเมนูน้อยลงในวันแรกที่ขึ้นฟีเจอร์นี้ เพราะตำแหน่งมาตรฐานเห็นทุกเมนูเหมือนเดิม)
8. ตำแหน่งมาตรฐานทั้ง 3 **ลบไม่ได้** (กันไม่ให้ระบบไม่มีตำแหน่งระดับ admin เหลืออยู่เลย) แต่ **แก้ชื่อและติ๊กเปิด/ปิดเมนูได้**
9. หน้า "ผู้ใช้งาน" (user management) เปลี่ยนจากเลือก role ตรงๆ เป็นเลือก "ตำแหน่ง" ให้แต่ละคน — ระบบจะ derive role (สิทธิ์พื้นฐาน) จากตำแหน่งที่เลือกให้อัตโนมัติ

## Non-goals / Anti-goals

- **ไม่** รื้อหรือเขียนใหม่ระบบ `hasPermission()` / role check ที่กระจายอยู่ทั่วแอป — ของเดิมทำงานต่อเหมือนเดิมทุกจุด
- **ไม่** เพิ่มระดับสิทธิ์ที่ 4/5 หรือสิทธิ์การกระทำแบบกำหนดเองต่อตำแหน่ง (เช่น "ตำแหน่งนี้ลบ booking ได้แต่ลบรถไม่ได้") — action-level permission ยังอิง 3 ระดับเดิมเท่านั้น สิ่งที่ตำแหน่งกำหนดเองได้คือ "ชื่อ" กับ "เห็นเมนูไหนบ้าง" เท่านั้น
- **ไม่** ทำ toggle ระดับเมนูย่อยในรอบนี้ (เช่น ซ่อนฟอร์ม "ความเร็ว" อันเดียวใต้ Complaints) — ของเดิมทุกคนเห็นเมนูย่อยเท่ากันหมดถ้าเห็นเมนูหลักนั้น เก็บไว้เป็นเฟสถัดไป
- **ไม่** แตะสิทธิ์พิเศษรายบุคคล 3 อย่างที่มีอยู่แล้ว (แก้เวลาหลังปิดงาน, ลบ Complaints, เข้าถึงชั่วโมงทำงานเป็นรายคน) — กลไกการ "มอบสิทธิ์พิเศษเฉพาะคน" แบบ capability grant ที่มีอยู่เดิมยังทำงานเหมือนเดิมทุกจุด
  - ข้อยกเว้นเดียว: เมนู **"ชั่วโมงทำงาน"** ทุกวันนี้โชว์ในแถบซ้ายถ้า `hasPermission('supervisor')` **หรือ** ผู้ใช้คนนั้นได้รับสิทธิ์พิเศษรายบุคคล — ของใหม่จะให้ "ตำแหน่งเห็นเมนูนี้ไหม" เข้ามาแทนที่เงื่อนไข `hasPermission('supervisor')` ตัวเดิม (เป็นอีกช่องทางหนึ่งที่ทำให้เห็นเมนูนี้ได้) ส่วนสิทธิ์พิเศษรายบุคคลที่มอบแยกไว้แล้วยัง **OR** เข้ามาเหมือนเดิมทุกประการ ไม่มีใครเห็นเมนูนี้น้อยลงจากที่เป็นอยู่
- **ไม่** ลบ/เปลี่ยนคอลัมน์ `role` เดิมในตาราง `users` — ยังต้องมีอยู่และเป็นค่าที่ถูกต้องเสมอ (ซิงก์จากตำแหน่งที่ผูกไว้) เพราะโค้ดเดิมทั้งแอปอ่านค่านี้โดยตรง

## Constraints

- ห้ามทำให้ผู้ใช้เดิมคนไหนเสียสิทธิ์หรือเห็นเมนูน้อยลงทันทีที่ฟีเจอร์นี้ขึ้น (migration ต้อง 1:1 กับสถานะปัจจุบัน)
- ทุก route guard ใหม่ต้องทำงานสอดคล้องกับ `AdminRoute`/route guard ที่มีอยู่แล้ว ไม่ขัดแย้งกัน (เช่น `/settings/users` ที่ยังต้องเป็น admin เท่านั้นเหมือนเดิม ไม่ว่าจะตั้งเมนูอะไรไว้)
- เครื่อง local ไม่มี `DATABASE_URL` ต่อฐานข้อมูลจริง (ทราบจากงานก่อนหน้านี้ในโปรเจกต์) — ตรวจสอบได้แค่ `tsc`/`eslint`/`vitest` และเปิดหน้าเว็บด้วย demo mode เท่านั้น การยืนยันกับฐานข้อมูลจริงต้องให้ผู้ใช้ทดสอบเองหลัง deploy

## สิ่งที่ตัดสินใจไว้แล้ว (ของผู้ใช้)

- สิทธิ์พื้นฐานของตำแหน่งใหม่ = เลือกจาก 3 ระดับเดิมของระบบเท่านั้น (ไม่ใช่สร้างใหม่)
- ปิดเมนู = ซ่อนจากแถบซ้าย **และ** บล็อกการเปิดผ่าน URL ตรง (อิง logic เดียวกับที่ `/settings` กัน staff อยู่แล้วตอนนี้)
- ระดับการติ๊กเปิด/ปิด = เฉพาะเมนูหลักเท่านั้น ไม่ลงเมนูย่อย (เผื่อเพิ่มละเอียดกว่านี้ได้ในอนาคต)
- เมนู "ตำแหน่งและเมนู" วางต่อจาก "ผู้ใช้งาน" ด้วย logic การแสดงผลเดียวกัน (admin เท่านั้น)
- กันการล็อกตัวเอง: สำหรับตำแหน่งที่สิทธิ์พื้นฐาน = admin เมนู **"ผู้ใช้งาน"** และ **"ตำแหน่งและเมนู"** ต้อง **เห็นเสมอ ติ๊กออกไม่ได้** ในหน้า add/edit ตำแหน่ง (ทั้ง UI ฝั่งหน้าเว็บ และตรวจซ้ำฝั่ง API ตอนบันทึก) — ป้องกันไม่ให้ไม่มีใครเข้าหน้าจัดการสิทธิ์ได้อีกเลย ตำแหน่งที่สิทธิ์พื้นฐานเป็น supervisor/staff ยังติ๊กเมนู 2 อันนี้ไม่ได้อยู่แล้วตามปกติ (เพราะไม่ใช่ admin) จึงไม่กระทบ

## สิ่งที่ปล่อยให้ผู้ลงมือทำตัดสินใจเอง (builder's call)

- ชื่อ/โครง schema ฐานข้อมูลจริง (ชื่อตาราง, เก็บรายการเมนูที่เห็นเป็น join table หรือ column เดียว, ชื่อ migration ไฟล์)
- รายการ "menu key" ทั้งหมดที่ map กับ `DOCK_NAV_ITEMS` ปัจจุบัน + ตำแหน่งของเมนูใหม่ 2 อัน ("ตำแหน่งและเมนู" และ "ผู้ใช้งาน" เอง) ในรายการนี้
- รูปแบบ API endpoint สำหรับ CRUD ตำแหน่ง (path, method, payload shape)
- โครงสร้าง component/dialog หน้า add-edit ตำแหน่งจริง (คัดลอกสไตล์ตามภาพอ้างอิง ปรับให้เข้ากับ design system เดิมของโปรเจกต์นี้ที่ใช้อยู่แล้ว ไม่ใช่ของแอปต้นแบบ)
- ชื่อเริ่มต้นของตำแหน่งมาตรฐาน 3 อัน — ค่าเริ่มต้น: ใช้ label เดิมที่มีอยู่แล้วในหน้า "ผู้ใช้งาน" ปัจจุบัน (admin / supervisor / staff) ไปก่อน เพื่อไม่ให้หน้าตาเปลี่ยนไปจากที่ผู้ใช้เคยเห็น — admin แก้ชื่อเองทีหลังได้
- รายละเอียด query/index การนับ "ผู้ใช้" ต่อแถวในตาราง list
- ตำแหน่งที่ไม่ติ๊กเมนูไว้เลยสักอัน — ปล่อยให้บันทึกได้ (ไม่บังคับต้องติ๊กอย่างน้อย 1 อัน) เพราะ `/fleet` (หน้าแรกหลัง login) ไม่ได้อยู่ในรายการเมนูที่ toggle ได้อยู่แล้ว จึงไม่มีทางถูกล็อกจนเข้าอะไรไม่ได้เลย เป็นแค่ UX ที่ไม่สวยถ้าเกิดขึ้นจริง ไม่ใช่บั๊ก
- การเปลี่ยนสิทธิ์พื้นฐาน/เมนูของตำแหน่ง มีผลกับผู้ใช้ที่ login ค้างอยู่ "ตอน login ครั้งถัดไป" เท่านั้น (เหมือนพฤติกรรมเดิมของระบบตอนแก้ role รายคนอยู่แล้ว — JWT ไม่ได้เช็คซ้ำกับ DB ทุก request) ไม่ทำอะไรเพิ่มเพื่อบังคับ logout ทันที
- สำหรับตำแหน่งที่สิทธิ์พื้นฐานเป็น supervisor/staff (ไม่ใช่ admin) checkbox ของเมนู "ผู้ใช้งาน"/"ตำแหน่งและเมนู" ในหน้า add/edit จะปิด/ซ่อนไปเลย (ไม่ใช่แค่ไม่ติ๊ก) เพราะ route ถูก `AdminRoute` กันไว้อยู่แล้วไม่ว่าจะตั้งเมนูอะไร — กันความสับสนว่าติ๊กแล้วทำไมเข้าไม่ได้
